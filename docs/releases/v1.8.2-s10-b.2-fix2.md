## 3. 原实现问题

旧生产路径由关键词、正则、前置 Handoff 判断和默认进入物业 Lane 共同决定控制权；证据门还会再次读取自然语言猜测事实类型。这会让一句话被多个字符串规则分别解释，也无法把“语义判断”和“允许执行什么”清楚分离。

## 4. 新结构化语义工作流

`自然语言与可见会话 → 一次 Flash 语义 Router → LaneDecision → 确定性 Lane 权限 → Lane 内 Agent → CapabilityDecision → AnswerContract → 受控回答/执行 → 最终事实门 → Trace/Evidence`

四条 Lane 为 `A_SAFETY_HANDOFF`、`B_PROPERTY_GOVERNED`、`C_ISOLATED_GENERAL`、`CLARIFY`。A 只做安全人工协同；B 只允许物业 Agent；C 只允许隔离通用 Agent；CLARIFY 只问一个决定下一步的问题。

## 5. 已删除或废弃的旧生产判断

- 生产 Coordinator 不再调用 `_decide_lane` 和默认 B 兜底。
- 不再用前置自然语言关键词决定 Handoff、写入或事实门。
- `_knowledge_evidence_decision` 改为只接受 AnswerContract，不再读取用户原句。
- Router 返回无效 JSON/Schema 时直接失败，不回退到字符串规则或另一次模型调用。
- 旧 `_capability_fallback` 仅为历史管理测试兼容保留，不在新生产链路取得控制权。

## 6. LaneDecision Schema

固定字段为：`lane`、`business_intent`、`reason_code`、`reason`、`confidence`、`requires_clarification`、`clarification_question`、`request_kind`、`allowed_domain`、`target_agent_id`、`decision_source`。Pydantic 校验 Lane、Domain、RequestKind、目标 Agent 和澄清字段的一致性。

## 7. AnswerContract Schema

固定字段为：`response_mode`、`evidence_required`、`evidence_requirements`、`skill_policy`、`rag_policy`、`tool_policy`、`write_policy`、`handoff_policy`、`forbidden_claims`、`decision_reason`。回答模式包括 `emergency_handoff`、`clarify_only`、`grounded_answer`、`realtime_read`、`controlled_write`、`safe_general`、`safe_refusal`。

## 8. 上下文隔离证据

Router 使用独立运行 session，只接收最近可见会话、当前问题和 Published Agent 能力摘要；LaneDecision、候选 Agent、Router JSON 和内部 reason 不进入垂直回答模型的用户可见历史。C Lane 从结构上跳过物业 Skill、RAG、MCP/Tool 与 ActionGateway。
