## P1-2: Badcase retest truthfulness

- The Badcase retest consumer now parses the canonical SSE `event` and `data` fields instead of treating every data payload as success.
- `event:error`, a non-complete terminal event, multiple terminal events, a missing terminal event, a missing answer, or a missing Trace is a controlled retest failure.
- A successful retest accepts only one `done(status=complete)`, a non-empty final answer, and a persisted complete Trace belonging to the same retest session.
- Failure returns HTTP 502, records only non-sensitive failure evidence, and does not change lifecycle state or successful retest fields. No synthetic `retest-*` Trace ID is created.
- The successful context records `run_status=complete`, the retest start time, persisted Trace status, and Trace/session binding. A changed status or apply anchor during the run invalidates the result.
- `verify-pass` requires a post-apply start and completion time, non-empty answer, matching Trace/context evidence, and a live complete Trace row for the same session.
- Linked Evaluation retests use the same execution-complete Trace contract while preserving the original Evaluation result separately as `evaluation_run_status`.

## S10-H.1: Evaluation terminal-evidence closure

- Evaluation no longer synthesizes `complete`, accepts `message_id` as a terminal event, or lets `final` substitute for the canonical SSE `done` event.
- Rule scoring starts only after exactly one parseable `done(status=complete)`, no `error` event, a non-empty answer, and a non-empty real `trace_id` have all been observed.
- The referenced Trace must already exist, have `status=complete`, and belong to the exact Evaluation session. Missing, failed, or cross-session Trace evidence is a controlled failed Run.
- Malformed or non-object `error`/`done` payloads, duplicate done events, unknown/non-complete status, missing terminal evidence, a stream interruption, and any business event after done are deterministic failures.
- A failed execution still creates exactly one failed Evaluation Run, retains any real Trace evidence obtained before failure, follows the existing Evaluation-to-Badcase linkage, and never opens Badcase `verify-pass`.
- The success and 22 failure variants use the real FastAPI route and real `_run_real_chat`; only the lower SSE source is deterministic. The complete S10-H suite passes 314 behavior checks with zero Provider-attempt delta in a `--network none` full-dependency API container.
- No schema, frontend, ordinary chat, runtime capability configuration, historical ledger, or RuntimeRelease changes are included. Active RuntimeRelease remains `rr_0027_3ec523af / v27`.

## S10-H.2: Evaluation runtime-terminal compatibility

- Protocol completeness and business outcome are now separate contracts. The canonical parser still requires exactly one parseable `done`, no error or interruption, a non-empty answer, and a persisted complete Trace for the exact Evaluation session, while accepting the real runtime terminal values `complete`, `paused`, and `completed` without rewriting any status.
- Any non-comment SSE field after the consumed done payload is a controlled failure. Only empty lines and transport comments beginning with `:` are allowed after done; a late event, default data, id, retry, or unknown field cannot rescue or alter a Run.
- Every case gets a visible deterministic `runtime_status` rule. Existing cases default to expected `complete`; new cases store the operator's `complete`, `paused`, or `completed` choice in `rubric.deterministic_assertions.expected_runtime_status`, with no schema change.
- A matching `paused` value still requires controlled-action evidence: a persisted same-run Proposal or session Draft, or an `action_gateway` waiting-confirmation tool call whose Proposal matches the current Trace event. `awaiting_parameters` cannot masquerade as owner confirmation.
- A matching `completed` value still requires a same-session Proposal, a persisted committed Receipt with a non-empty resource ID, and a matching current-Trace gateway commit event. A Proposal may truthfully originate from a prior Trace in the same session; an old Receipt or payload-only claim cannot pass.
- Status agreement only enters the existing Agent, Skill, RAG, Tool, terminology, prohibition, handoff, and operator-rubric checks; it never grants PASS by itself. Any failed rule keeps the linked Badcase from opening `verify-pass`.
- Full-dependency acceptance runs the real FastAPI route and real `_run_real_chat`, replacing only the lower deterministic SSE source: **PASS, 441 behavior checks, zero Provider-attempt delta**, in a `--network none` container with a fresh temporary SQLite directory and no Provider credentials.
- Two older direct rule-engine fixtures now supply their previously implicit successful terminal value as explicit `status=complete`; production behavior is not relaxed. Their S6 Golden Set and V1.6 quality-governance regressions pass under the new fail-closed contract.
- Frontend changes are limited to one advanced expected-result select plus Chinese expected/actual labels. No database migration, historical rewrite, runtime capability change, or RuntimeRelease is included; active RuntimeRelease remains `rr_0027_3ec523af / v27`.
